# Stripe Billing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A premium monthly subscription via Stripe that unlocks **(1) the AI Coach** and **(2) a higher bucket cap (Free 5 → Premium 15)**. Free users get everything else (bank sync, auto-categorization, up to 5 buckets); premium unlocks the Coach chat + suggestions and up to 15 buckets. A Stripe webhook flips a `premium` flag on the user; both the Coach and the buckets cap read it via the shared `usePremium` hook.

**Architecture:** Stripe Checkout (hosted, `mode: subscription`) is created by a server endpoint; the user pays on Stripe's page; a **webhook** (Stripe → our server, signature-verified with the raw body) updates the user's `premium` flag in Firestore. The Coach's existing `isPremium` seam reads that flag. Server logic lives in **Next.js route handlers** (`app/api/billing/*`) — this is HTTP webhook + redirect flow, which fits Next routes cleanly and needs the raw request body for signature verification (a Cloud Function would also work, but the webhook raw-body handling is simplest in a Next route). Stripe secret + webhook secret stay server-side.

**Tech Stack:** `stripe` Node SDK, Next.js 16 route handlers (`app/api/...`), Firebase admin SDK (server) to set `premium`, Firestore client to read it, Vitest.

## Global Constraints

- **Secrets server-side only:** `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_ID` in server env — never `NEXT_PUBLIC_` (except the publishable key if Checkout-redirect needs it; hosted Checkout via a server-created session URL avoids even that). No secret in the client bundle.
- **Webhook signature verification is mandatory:** the webhook route MUST verify `stripe-signature` against the **raw request body** using `stripe.webhooks.constructEvent`. Never trust an unverified webhook. In Next 16 route handlers, read the raw body via `await req.text()` (not `req.json()`) so the signature matches.
- **Premium flag is server-authoritative:** only the webhook (server, admin SDK) sets `users/{uid}.premium`. The client only READS it (and Firestore rules already let a user read their own doc). The client can never set its own premium.
- **Map Stripe customer ↔ user:** store `stripeCustomerId` on the user (or a lookup) so webhook events (which carry the customer, not our uid) resolve to the right user. Pass `client_reference_id = uid` (and/or metadata) into Checkout so the first event can bind them.
- **Idempotent webhook:** Stripe may deliver an event more than once — handling must be idempotent (setting a boolean flag is naturally idempotent; if storing more, guard on event id).
- **Money not our concern here:** Stripe handles the actual charge; we only flip a flag. No integer-cent logic in this plan.
- **Reuse:** the Coach's `isPremium` seam (from the Coach plan); `useAuth` for the current uid; admin SDK patterns from the functions/bank work (but here in a Next route, using `firebase-admin` initialized server-side).

## Scope

**IN:** a `usePremium()` client hook (reads `users/{uid}.premium`); a create-checkout-session route; a signature-verified webhook route that flips `premium` on `checkout.session.completed` / `customer.subscription.deleted`; an Upgrade screen/paywall that replaces the Coach input for free users; wiring the Coach `isPremium` seam to the real flag.

**DEFERRED (documented, NOT built):**
- Stripe Customer Portal (manage/cancel subscription) — link out later; MVP: subscribe only. (Cancel still works via `customer.subscription.deleted` webhook downgrading them.)
- Proration/annual plans/multiple tiers — single monthly price.
- x402 agent micropayments (the v2/v3 roadmap item — untouched).
- Dunning/failed-payment UX beyond the subscription-deleted downgrade.

## File Structure

- `lib/billing/usePremium.ts` — client hook: subscribe to `users/{uid}` doc, expose `{ premium, loading }`.
- `lib/server/firebaseAdmin.ts` — server-only firebase-admin init (for the webhook route to write with admin rights). (If one already exists from functions, reuse the pattern; this is a Next-server instance.)
- `app/api/billing/checkout/route.ts` — POST: create a Checkout Session (`mode: subscription`, `client_reference_id: uid`, price = `STRIPE_PRICE_ID`), return the session URL.
- `app/api/billing/webhook/route.ts` — POST: verify signature (raw body), handle `checkout.session.completed` (set premium true) + `customer.subscription.deleted` (set false).
- `lib/billing/webhookHandlers.ts` — pure-ish `handleStripeEvent(event, admin)` so the flag-flip logic is testable without HTTP.
- `components/billing/UpgradeCard.tsx` — the paywall/upgrade CTA shown to free users on Coach.
- `app/(app)/coach/page.tsx` (modify) — use real `usePremium()` for the gate.

## Self-Review

- **Spec coverage:** Stripe subscription (Tasks 1–3), webhook flips premium (Tasks 2–3), premium gates the Coach (Tasks 1,4), free tier keeps everything else. Matches the "Coach-only gate" decision.
- **Security:** secrets server-side; webhook signature-verified against raw body; premium is server-authoritative (client read-only). Called out in Global Constraints.
- **Idempotency:** flag-flip is naturally idempotent; note if extending to stored events.
- **Testability:** the risky bits are unit-tested without live Stripe — `handleStripeEvent` (pure, injected setter) and the webhook route's signature verification (via `generateTestHeaderString`). Checkout creation + real end-to-end payment is verified in Stripe test mode.
- **OOM guard:** hook mocks use stable module-level refs.
- **Placeholders:** Tasks 1,2,4 carry test code; Task 3 gives exact route contracts + the raw-body/signature requirement (real Stripe verified in test mode, not mocked into false confidence).
