# AI Coach Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A conversational Gemini coach that sees the user's bucket state and recent transactions, answers questions, predicts shortfalls, and proposes concrete **suggested actions** (e.g. "shift €50 from Savings to Nights out?") the user can Apply or Dismiss — where Apply performs a safe, confirmed change.

**Architecture:** The Gemini call runs server-side in a Cloud Function (`coachReply` callable) — the key stays server-only. The function builds a compact context (buckets: name/percent/remaining/allocated; a few recent transactions) and asks Gemini for a reply that is EITHER plain advice OR a structured **suggestion** (a bounded, whitelisted action). The client renders the chat and, for a suggestion, an Apply/Dismiss card; **Apply calls a separate, deterministic callable** that validates and performs the action (never Gemini moving money directly). MVP action type: `rebalance` (move a percentage/amount between two buckets' future split, or a one-off transfer of `remaining` between buckets). All money math reuses existing deterministic code; Gemini only proposes, code disposes.

**Tech Stack:** `@google/genai` (server-side, Cloud Functions), Firebase callable functions + Firestore admin SDK, Next.js 16 client chat UI, Vitest.

## Global Constraints

- **Gemini key server-side only** (Functions env). Never `NEXT_PUBLIC_`, never client.
- **AI proposes, code disposes:** Gemini NEVER moves money. It returns a *suggestion* (typed, bounded); a separate deterministic callable validates + applies it only on explicit user Apply. Any suggestion referencing a nonexistent bucket or an out-of-range amount is rejected by the validator, not trusted.
- **Read-only context:** the coach reads bucket state + recent transactions; it does not get write access. Money integer cents; any applied action conserves (no cents created/lost) and is idempotent.
- **Structured output:** Gemini responds with constrained JSON — `{ reply: string, suggestion?: { type: "rebalance", fromBucketId, toBucketId, amount } }` — `fromBucketId`/`toBucketId` constrained to the user's real bucket ids (enum); validator re-checks server-side.
- **Premium-gated (wiring only here):** the Coach is the premium feature (billing plan gates it). This plan builds the Coach; the actual gate/paywall is enforced in the Stripe plan. Leave a single `isPremium` check point (defaulting to allowed in dev) so billing can flip it — don't build the paywall here.
- **Reuse:** bucket read via existing store helpers; `formatEuros` for display; the chat UI matches the approved Coach mockup (message bubbles + inline Apply/Dismiss suggestion card). No emojis; dark tokens.

## Scope

**IN:** `coachReply` callable (Gemini, context-building, structured reply+optional suggestion); `applyCoachSuggestion` callable (validates + performs a `rebalance`, idempotent); client Coach chat UI with message bubbles + Apply/Dismiss suggestion card; a single premium-check seam.

**DEFERRED (documented, NOT built):**
- Persisted chat history across sessions (MVP: in-memory per session, or store last N — keep minimal; note choice).
- More action types (create bucket, change a bucket's percent long-term, schedule) — MVP is a one-off `rebalance` transfer of `remaining` between two buckets.
- Streaming responses (MVP: single response).
- Proactive coach messages pushed without the user asking (the shortfall prediction shows when the user opens Coach / asks).

## Task 1: Shared suggestion types + validator (pure)

**Files:**
- Create: `lib/coach/suggestion.ts`
- Test: `lib/coach/suggestion.test.ts`

**Interfaces:**
- `type CoachSuggestion = { type: "rebalance"; fromBucketId: string; toBucketId: string; amount: number }` (amount = positive integer cents).
- `type CoachReply = { reply: string; suggestion?: CoachSuggestion }`.
- `validateSuggestion(s: CoachSuggestion, buckets: { id: string; remaining: number }[]): { ok: true } | { ok: false; reason: string }` — reject if: from/to not in buckets; from === to; amount <= 0 or not integer; amount > from bucket's `remaining` (can't move more than is there). This is the single source of truth for both UI and server.

- [ ] **Step 1: Write the failing test**

`lib/coach/suggestion.test.ts`:
```ts
import { describe, it, expect } from "vitest";
import { validateSuggestion, type CoachSuggestion } from "@/lib/coach/suggestion";

const buckets = [{ id: "save", remaining: 50000 }, { id: "fun", remaining: 1500 }];
const base: CoachSuggestion = { type: "rebalance", fromBucketId: "save", toBucketId: "fun", amount: 5000 };

describe("validateSuggestion", () => {
  it("accepts a valid rebalance within available funds", () => {
    expect(validateSuggestion(base, buckets)).toEqual({ ok: true });
  });
  it("rejects an unknown bucket", () => {
    expect(validateSuggestion({ ...base, toBucketId: "ghost" }, buckets).ok).toBe(false);
  });
  it("rejects moving more than the source has", () => {
    expect(validateSuggestion({ ...base, amount: 60000 }, buckets).ok).toBe(false);
  });
  it("rejects same-bucket / non-positive / non-integer amounts", () => {
    expect(validateSuggestion({ ...base, toBucketId: "save" }, buckets).ok).toBe(false);
    expect(validateSuggestion({ ...base, amount: 0 }, buckets).ok).toBe(false);
    expect(validateSuggestion({ ...base, amount: 12.5 }, buckets).ok).toBe(false);
  });
});
```

## Task 3: applyCoachSuggestion callable (deterministic, idempotent)

**Files:**
- Modify: `functions/src/coach.ts`, `functions/src/index.ts`, `functions/src/store.ts`
- Test: manual/E2E; the money move mirrors the tested rebalance semantics.

**Interfaces:**
- `applyCoachSuggestion` = auth-gated `onCall({ suggestion, suggestionId })` → validates with `validateSuggestion` against fresh bucket state, then in a Firestore transaction moves `amount` cents: `from.remaining -= amount`, `to.remaining += amount`. **Idempotent** via a marker doc `users/{uid}/coachActions/{suggestionId}` (client generates a stable id per suggestion): if the marker exists, no-op. Read-before-write; reject (throw `HttpsError("failed-precondition")`) if validation fails at apply time (e.g. balance changed).
- Store helper `applyRebalance(uid, fromId, toId, amount, actionId)` implementing the above.

- [ ] **Step 1: Implement `applyRebalance` in `store.ts`** — transaction: read marker (return if exists) + read both buckets; re-validate (from has ≥ amount); write marker + `increment(from.remaining, -amount)` + `increment(to.remaining, +amount)`. All reads before writes.

- [ ] **Step 2: Implement `applyCoachSuggestion`** — auth-gate; call `validateSuggestion`; call `applyRebalance`; return `{ ok: true }`.

- [ ] **Step 3: Export + typecheck** — add to index; `cd functions && pnpm exec tsc --noEmit` + root `pnpm exec tsc --noEmit` clean.
